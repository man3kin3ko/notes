## Архитектура кластера

Kubernetes - это платформа для автоматизации развертывания, масштабирования и управления контейнерами. 

Кластер разворачивается на множестве физических или виртуальных серверов, называемых node (узлами). Ноды, использующиеся для управления внутренним состоянием кластера, называются master node (мастер-узел). Ноды, непосредственно запускающие контейнеры, называются worker node (рабочий узел).

Мастер-узел состоит из следующих компонентов: 
- `kube-scheduler` - определяет, на каком (рабочем) узле будет запущен контейнер
- `kube-apiserver` - создает единый интерфейс между мастер- и рабочими узлами, а также для администрирования через `kubectl`
- `kube-controller-manager` - управляет состоянием кластера при помощи контроллеров (перезапускает упавшие контейнеры, следит за доступностью нод, и т.д.)
- etcd - хранит все данные кластера, включая конфигурации, роли, неймспейсы и сетевые политики

Один или несколько мастер-узлов называются Control Plane, его можно развернуть при помощи инструмента `kubeadm`. Как правило, он состоит из нескольких узлов для увеличения доступности (high avaliability). 

> 💡 Мастер-ноды синхронизируют etcd между друг другом, используя алгоритм консенсуса Рафта, поэтому их должно быть нечетное количество.

Рабочий узел состоит из компонентов:
- `kubelet` - агент, получающий от API-сервера манифесты на запуск контейнеров
- container runtime (CRI) - демон Docker, получающий задачи от `kubelet`
- `kube-proxy` - поддерживает сетевые правила на узле и отвечает за балансировку нагрузки между контейнерами

## Объекты

Объекты это сущности, которые сохраняются в etcd и представляют желаемое состояние кластера.  Если у объекта есть API интерфейс для взаимодействия, он называется ресурсом. Ресурс декларативно описывается *манифестом*.

Ресурсы делятся на:
- Встроенные (built-in)
- Пользовательские (CRD, Custom Resource Definitions)

### Workload resources

Рабочая нагрузка (workload) представляет собой описание приложения, состоящего из подов. 

Манифест рабочей нагрузки передается к `kube-apiserver`. Он проверяет аутентификацию, авторизацию (RBAC), валидирует запрос по схеме и сохраняет объект в etcd. В зависимости от типа рабочей нагрузки - Deployment, StatefulSet, DaemonSet или Job - `kube-controller-manager` запускает соответствующий контроллер, который создает под. `kube-scheduler` отслеживает созданные поды и планирует их запуск на узлах.

Под *подом* подразумевается группа из одного и более контейнеров, объединенные контекстом (shared context), такими, как хранилища, сеть и спецификация на запуск, иными словами, он представляет собой "логический хост". Например, помимо контейнера с приложением, в поде может быть запущен ephemeral container для дебага. В контекст входят namespaces, cgroups и chroot - механизмы, отделяющие контейнер от хоста ([[Docker#^d48fbe]]).

Дополнения (аддоны) - это компоненты, запускаемые в виде подов в кластере для предоставления системных функций - управления сетью, логгирования, мониторинга. Включенные дополнения хранятся на мастер-узле в `/etc/kubernetes/addons` в виде манифеста. CoreDNS и Dashboard являются частью k8s, а такие как NGINX Ingress Controller разрабатываются сторонними разработчиками и устанавливаются через менеджер Helm.

## etcd

Инстансов etcd может быть несколько, поэтому лучшей практикой является создание отдельного CA для общения инстансов etcd друг с другом и для общения с ворклоад нодами через API.

По умолчанию секреты в etcd хранятся (at rest) в открытом виде.

> 💡При включении шифрования etcd секреты шифруются только при записи, поэтому после включения необходимо вручную зашифровать все имеющиеся секреты с помощью kubectl
